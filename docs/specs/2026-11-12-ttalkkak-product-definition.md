# ttalkkak 제품 정의 (2026-11-12)

이 문서는 ttalkkak이 무엇인지와 만드는 순서를 정한다. 각 프로젝트의 세부 설계는 그 프로젝트를 시작할 때 따로 쓴다. "(판단)"이라고 표시한 항목은 사용자가 직접 말한 것이 아니라 작성자가 정한 것이다.

## 1. 한 문장

**칩 회사가 칩과 함께 주는 AI 인프라 소프트웨어 스택. 클라우드 사업자가 그 칩 위에서 AI 에이전트 서비스를 바로 운영하게 해 준다.**

NVIDIA가 GPU에 NIM·Dynamo 같은 자기 소프트웨어를 얹어 주는 것과 같은 자리다. HyperAccel이나 FuriosaAI가 "우리 칩을 사면 이것까지 온다"고 내놓을 물건을 만든다.

## 2. 왜 만드나

- 사용자는 HyperAccel·FuriosaAI 지원을 준비하고 있다. 두 회사가 만들고 싶어 할 소프트웨어를 미리 만들어 보여 주는 것이 목적이다.
- 지원이나 면접 날짜는 정해지지 않았다. 그래서 기능 수보다 하나씩 제대로 끝내는 것을 우선한다.

## 3. 등장인물과 각자의 화면

| 누구 | 예 | 무엇을 하나 | 화면 |
|---|---|---|---|
| 칩 회사 | HyperAccel, FuriosaAI | ttalkkak을 만들어 칩과 함께 준다. 자기 칩과 추론 엔진을 ttalkkak에 끼운다 | (없음. 코드의 끼우는 자리) |
| 클라우드 사업자 | 네이버클라우드 | 칩과 ttalkkak을 데이터센터에 깔고 서비스를 운영한다 | 웹 콘솔 |
| 클라우드 이용자 | 네이버클라우드 고객 | 돈을 내고 에이전트를 쓴다 | 터미널 (`ttalkkak`) |

### 3.1 이용자가 겪는 것

가입하고 결제한 직후: 터미널에 `ttalkkak`을 설치하고, 브라우저로 로그인하면 바로 에이전트를 쓴다. 코드 분석, 버그 수정, 유튜브 요약 같은 일을 시킨다. 쓴 만큼의 토큰과 예상 요금이 보인다.

### 3.2 사업자가 겪는 것

첫날 "이거 좋네"라고 느끼는 이유:

1. 고객 관리가 편하다(고객, 키, 사용량, 청구를 한 곳에서).
2. 서비스를 돌리면서 모델을 바꾸거나 새 버전으로 올려도 문제가 없다.
3. 사용자가 여럿 몰려도 잘 대응한다.
4. 안 쓸 때는 알아서 줄여 절약한다.
5. 작은 모델로 큰 모델만큼 좋은 답을 내게 돕는다.
6. 그 밖에 실제 분산 환경에 필요한 기능이 여럿 있다.

### 3.3 칩 회사가 끼우는 자리 (판단)

칩 회사 제품이 되려면 "우리 칩 + 우리 엔진"을 핵심 코드를 고치지 않고 넣을 수 있어야 한다. 지금 코드는 하드웨어가 `nvidia`와 `amd` 두 값으로 고정되어 있다. 지금 그 자리에는 RTX 3060 Ti와 vLLM이 들어간다. 이 자리를 여는 작업을 어느 프로젝트에 넣을지는 5절 "남은 결정"에 있다.

## 4. 시연 장면

면접관 앞 맥북 화면. 맥북은 **이용자 환경**이고, 서비스는 집에 켜 둔 **데스크탑(RTX 3060 Ti 8GB)** 에서 돈다. 맥북이 원격(Tailscale)으로 붙는다.

- **웹 콘솔이 주인공**이다(구성안 B). AWS 콘솔 같은 웹 콘솔 하나에 개요, 모델, 테넌트, 사용량, 에이전트 세션이 탭으로 있다. 실시간 지표가 보인다.
- **사용자 터미널은 실제 터미널 창**으로 옆에 띄운다. 터미널에서 일을 시키면 콘솔의 세션 탭에 진행이 실시간으로 보인다.
- 시연 전용 화면은 따로 만들지 않는다. 운영 화면이 곧 데모다. (판단)
- 면접관이 "지금 진짜 모델이 돌고 있나요?"라고 물으면 이렇게 답할 수 있어야 한다: "네, 진짜 돌고 있습니다. 작은 모델로도 높은 성능 지표를 내는 기능을 넣었고, 여러 사용자가 동시에 요청해도 빠르게 답합니다. 분산 환경입니다."
- 원격 연결이 끊길 때를 대비해 녹화본을 예비로 둔다. (판단)

## 5. 목표, 하지 않는 것, 피해야 할 모습

### 목표

- 3.2절의 기능들이 데스크탑에서 실제로 돈다.
- 앞세우는 두 가지는 **작은 모델 증폭**과 **몰려도 버티기**다.

### 피해야 할 모습 (가장 중요)

면접관이 **"완성도가 낮네요. 애들 장난인가요?"** 라고 말하는 것. 기능이 전부 있어도 이 반응이 나오면 실패다.

이를 막는 원칙 (판단, 사용자에게 제안하고 반대 없이 진행):

- "된다"고 말하는 기능은 데스크탑 실기에서 돌려 보고 숫자를 남긴 것만 인정한다.
- 화면에 있는 버튼은 전부 동작한다.
- 안 되는 기능은 숨기지 않고 "아직 안 됨"으로 적는다.
- 측정하지 않은 원인은 "원인 미확인"으로 쓴다.
- 기능 하나를 실기 검증까지 끝낸 뒤 다음으로 넘어간다. 어느 시점에 멈춰도 "여기까지는 진짜로 된다"고 말할 수 있게 한다.

### 한 구성에 다 올린다 (사용자 결정)

모든 기능을 작은 모델 하나(1.5B급)로 통일한 **한 구성**에서 동시에 보인다. 기능마다 구성을 바꾸지 않는다.

- 이유: 시연에서 "진짜 돌고 있고, 증폭도 되고, 여러 사용자도 받는다"가 한 번에 성립해야 한다. 작은 모델의 부족함은 증폭으로 메운다.
- 대가: 에이전트가 할 수 있는 일의 수준이 낮아진다. 시연 과제는 이 모델이 실제로 해내는 범위에서 고른다.
- 8GB에서 복제본, 여러 번 풀기, 무중단 교체(교체 중 모델 두 개 적재)가 메모리를 나눠 쓴다. 복제본이 실제로 몇 개 올라가는지는 프로젝트 2에서 측정하고, 그 결과로 조정한다.

### 정직하게 말해야 하는 한계

- **분산**: GPU 한 장 위에 모델 복제본 여러 개다. 기계 여러 대가 아니다. 8GB라서 1.5B급 모델 2~3개가 한계일 것으로 본다(측정 전 추정).
- **작은 모델의 능력**: 8GB에 올라가는 모델(1.5B~7B)은 버그 수정처럼 여러 단계를 스스로 이어 가는 일에서 자주 틀린다. 시연 과제는 작은 모델이 실제로 해내는 범위에서 고르고, 그 범위는 측정해서 정한다.
- **"큰 모델만큼"의 기준** (판단): 8GB에는 큰 모델이 올라가지 않는다. 비교 대상은 프로젝트 3 설계에서 정하되, 기본안은 (a) 같은 GPU에 올라가는 더 큰 모델(7B급) 한 번 풀기와 (b) 외부 API의 큰 모델(이미 지원하는 `nim:` 경로)이다. 검증 가능한 문제(수학, 코드)에서만 주장한다.
- **칩**: HyperAccel LPU나 Furiosa RNGD 실물은 없다. 끼우는 자리만 만들고, 실제로 끼워 보는 것은 NVIDIA GPU뿐이다.

### 하지 않는 것 (판단)

- 실제 결제. 요금은 추정이고 청구서 파일까지만 만든다(Stage 5 결정 유지).
- 기계 여러 대로 된 실제 클러스터 구성.
- 에이전트 여러 개가 협업하는 기능. 사용자가 말한 "여러 agent들이 하는 작업들"은 "요즘 에이전트들이 흔히 하는 일들"로 해석했다.

### 남은 결정


- 칩 회사가 끼우는 자리(3.3절)를 어느 프로젝트에서 열지. 작성자 제안: 프로젝트 2를 시작할 때 엔진과 하드웨어 설정을 건드리게 되므로 그때 같이 설계한다.

## 6. 만드는 순서

프로젝트 다섯 개다. 하나씩 설계하고, 만들고, 데스크탑에서 검증한 뒤 다음으로 간다.

| 순서 | 프로젝트 | 끝났다는 기준 |
|---|---|---|
| 1 | **뼈대 실증** | 지금까지 만든 것(게이트웨이, 고객 관리, 로그인, 콘솔, 청구)이 데스크탑에서 처음부터 끝까지 실제로 돈다. 소개 문서(README)가 이 정의서의 정체성으로 바뀐다 |
| 2 | **몰려도 버티기** | 복제본 여러 개와 라우팅이 돈다. 콘솔에 실시간 지표와 용량·여유가 보인다. 용량 지표로 복제본이 자동으로 늘고 준다(최소 1개). 부하를 건 실측 숫자가 있다 |
| 3 | **작은 모델 증폭** | 여러 번 풀고 고르기가 돈다. 정확도와 답 하나당 원가의 실측 숫자가 콘솔에 보인다 |
| 4 | **에이전트 런타임** | 터미널 에이전트가 도구와 스킬을 쓴다. 콘솔에 세션 탭이 있다 |
| 5 | **무중단 교체와 유휴 절약** | 서비스를 멈추지 않고 모델을 교체한다. 안 쓸 때 복제본을 0개까지 내려 전력을 아끼고, 요청이 오면 다시 켠다 |

순서의 이유 (판단):

- 1번이 먼저인 이유: Stage 1~5는 단위 테스트만 통과했고 실제 GPU에서 처음부터 끝까지 돌린 적이 없다. "애들 장난" 반응을 막으려면 여기부터다.
- 4번이 2·3번 뒤인 이유: 2번과 3번은 지금 있는 단순 대화 콘솔로도 보여 줄 수 있다. 작은 모델로 도구를 쓰는 에이전트는 3번의 증폭이 있어야 쓸 만해진다.

### 프로젝트 1의 범위

새 설계 없이 이미 있는 계획을 실행한다.

- `docs/plans/2026-11-11-ttalkkak-stage5.md`의 Task 12, 13과 `docs/desktop/stage5-desktop.md`
- README를 이 정의서의 정체성으로 다시 쓴다. 처음의 정체성("모델에 맞는 서빙 설정을 골라 검증해 주는 도구")은 제품의 중심이 아니라, 사업자가 새 모델을 올릴 때 쓰는 기능 하나("이 모델을 이 칩에 올려도 되는지 확인")로 설명한다. (판단)
- `stage5` 브랜치를 main에 합친다. `ui-polish`는 이미 `stage5`에 들어 있어서 따로 합칠 것이 없다(확인함). push는 사용자 확인 후에 한다.
- **hxccl 선행 조건은 풀렸다.** `docs/desktop/stage5-desktop.md`의 "hxccl B+C가 끝난 뒤 시작" 조건은 hxccl v0.2가 main에 merge되면서(2026-11-12) 충족됐다. 바로 시작할 수 있다.
- **맥북 원격 경로를 검증 범위에 넣는다.** (판단) Task 13은 데스크탑 안에서만 확인한다. 시연은 맥북이 Tailscale로 붙는 장면이므로, 맥북에서 `ttalkkak login`(브라우저 로그인) → 대화 → 웹 콘솔 열기까지 되는지를 프로젝트 1에서 확인한다. 호스트 이름, TLS 인증서, 로그인 주소가 원격에서도 맞아야 한다. **방법(사용자 결정):** 맥북에 정식 Tailscale 앱을 설치하고, 데스크탑의 MagicDNS 이름과 `tailscale cert` 인증서를 쓴다. SSH 터널과 자체 서명 인증서는 쓰지 않는다. 절차는 `docs/desktop/stage5-desktop.md` 3.5절.
- **웹 화면의 "서빙 실행" 단계 화면**(모델 고르기 → 스킬 → 실행 → 결과)은 지우지 않는다. 콘솔 안에서 "새 모델을 올려도 되는지 확인"하는 기능으로 남긴다. (판단)

## 7. 지금 있는 것 (2026-11-12 기준)

- 브랜치 `stage5`: 약 6,100줄, 테스트 295개 통과(맥, GPU 없음). 게이트웨이 매니페스트(Envoy AI Gateway + llm-d + vLLM), 테넌트와 키, 브라우저 로그인, 원가 측정, 청구, 운영 웹 화면, 단순 대화 콘솔.
- 실제 GPU에서 처음부터 끝까지 돌린 적은 없다.
- 데스크탑에는 저장소를 clone하고 k3s를 켠 상태까지 확인했다. 그 뒤 진행 여부는 확인하지 못했다(데스크탑 offline).
- 사용자 에이전트는 도구 없이 대화만 한다. 운영자용 에이전트는 LangGraph를 감싼 39줄로 따로 있다.

## 8. 만드는 방식

- 맥에서 설계, 구현, GPU 없이 가능한 테스트를 한다. GPU가 필요한 검증은 데스크탑에 지시문(`docs/desktop/`)으로 넘긴다.
- 프로젝트마다 설계 문서 → 계획 → 구현 → 독립 리뷰 → 데스크탑 검증 순서를 따른다.
- 결정은 `docs/stage5-ledger.md` 방식으로 번호를 붙여 남긴다.
