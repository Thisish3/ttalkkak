# ttalkkak 프로젝트 2 설계: 몰려도 버티기 (2026-11-12)

상위 문서: `docs/specs/2026-11-12-ttalkkak-product-definition.md`(제품 정의서). 이 문서는 그 6절 표의 프로젝트 2다. "(판단)"은 사용자가 직접 말하지 않고 작성자가 정한 것이다.

## 1. 의도

시연 장면(사용자 결정): 면접관 앞에서 여러 사용자가 동시에 요청해도 응답이 빠르게 나오는 지표를 보여 준다. 판단 기준은 **복제본 1개일 때와 3개일 때의 비교**다.

같은 프로젝트에서 **칩 회사가 끼우는 자리**도 연다(제품 정의서 3.3절, 5절 "남은 결정"). 사용자 결정: **설정 파일 하나로 칩을 끼운다.**

## 2. 먼저 확인할 위험 (설계의 전제)

GPU 한 장에서 vLLM 복제본 1개는 이미 요청을 묶어서 처리한다(continuous batching). 같은 GPU에 복제본 3개를 띄우면 계산과 메모리를 나눠 쓰고, 각자의 KV 캐시가 작아진다. **그래서 3개가 1개보다 빠르지 않을 수 있다.** 아직 측정하지 않았다.

- 측정: `docs/desktop/spike-replicas.md`(데스크탑, 30~60분, Docker만 사용). 결과는 `docs/results/spike-replicas/`.
- 사용자와 합의한 진행: 이 측정을 먼저 하고 그 결과로 시연 내용을 정한다.

결과에 따라 갈라지는 부분 (판단):

| 측정 결과 | 시연에서 보여 줄 것 | 이 설계에서 바뀌는 것 |
|---|---|---|
| 3개가 1개보다 빠르다 | 부하 시험으로 1개 vs 3개를 겹쳐 그려 비교 | 없음 |
| 1개가 빠르거나 차이가 없다 | 같은 비교를 보여 주되 결론을 정직하게: "GPU 한 장에서는 복제본보다 배치가 낫다. 복제본은 칩이 여러 장일 때와, 하나가 죽어도 서비스가 멈추지 않게 할 때 쓴다". 복제본 하나를 꺼도 응답이 이어지는 장면을 추가 | 4.4절 "복제본 하나 끄기" 버튼이 필수 기능이 된다 |

어느 쪽이든 부하 시험, 실시간 지표, 칩 설정 파일은 똑같이 필요하다. 그래서 측정 전에도 이 부분은 계획과 구현을 시작할 수 있다.

## 3. 칩 설정 파일

### 3.1 지금 칩 종류가 박혀 있는 곳 (조사 결과)

| 곳 | 하는 일 |
|---|---|
| `platform.py` | 엔진 컨테이너 이미지, Docker에서 칩을 연결하는 옵션 |
| `schemas.py` `GpuInfo.vendor` | `Literal["nvidia", "amd"]` |
| `probe/gpu.py` | 칩 찾기와 메모리(`nvidia-smi` / `amd-smi`) |
| `export/common.py` `gpu_key` | 쿠버네티스 자원 이름(`nvidia.com/gpu` / `amd.com/gpu`) |
| `export/kserve.py`, `export/llmd.py`, `export/dynamo.py` | 배포용 이미지와 대상 제한 |
| `cost/power.py` | 전력 읽기(`nvidia-smi`) |
| `gateway/observability.py`, `gateway/versions.py` | 지표 수집기(DCGM)와 대시보드·경보의 지표 이름 |

### 3.2 형식 (사용자가 승인한 초안)

```yaml
# chips/<이름>.yaml
name: hyperaccel-lpu
vendor: HyperAccel
detect:                         # 칩 찾기
  command: ["<칩 상태 명령>", "--json"]
  name: "$.devices[0].name"
  memory_mib: "$.devices[0].memory_mib"
engine:                         # 이 칩에서 모델을 띄우는 컨테이너
  image: "<레지스트리>/<엔진>:<버전>"
  api: openai                   # OpenAI 호환 API를 낸다고 약속
  port: 8000
  args: ["--model", "{model}", "--max-model-len", "{max_len}"]
  health: /health
docker:
  devices: ["/dev/<칩 장치>"]
kubernetes:
  resource: "<회사>.com/lpu"
telemetry:                      # 전력과 상태 (원가 계산과 대시보드)
  power_watts: ["<칩 상태 명령>", "--power"]
  exporter_image: "<지표 수집기 이미지>"   # 없으면 비움
  metrics:                      # 공통 이름 ← 칩 지표 이름
    utilization: "<지표>"
    power: "<지표>"
    memory_used: "<지표>"
    temperature: "<지표>"
```

검토 후 보탠 것 (판단): 지금 코드는 엔진(vLLM, SGLang)마다, 그리고 배포 대상(llm-d, KServe)마다 이미지가 따로 있다. 동작을 바꾸지 않으려면 위 형식에 두 칸을 더한다. `engine`은 엔진 이름별 목록(`engines: {vllm: {...}, sglang: {...}}`)이 되고, 배포용 이미지는 `export: {llmd: ..., kserve: ...}`에 둔다. 칩 회사가 엔진을 하나만 내면 `engines`에 하나만 쓰면 된다. 사용자가 승인한 모양(파일 하나, 칸 이름)은 그대로다.

### 3.3 동작

- 기본 설정 파일 두 개를 함께 낸다: `chips/nvidia-gpu.yaml`, `chips/amd-gpu.yaml`. 3.1절의 박힌 값을 모두 이 두 파일로 옮긴다. 옮긴 뒤 기존 테스트가 그대로 통과해야 한다(동작이 바뀌지 않는다).
- 새 칩은 `chips/`에 파일 하나를 추가하는 것으로 끝난다. 코드 수정은 없다.
- 설정 파일을 읽을 때 형식을 검사한다. 빠진 칸이나 잘못된 값은 칸 이름을 넣은 한국어 오류로 알린다.
- `detect`가 여러 설정 파일에서 성공하면 먼저 찾은 것을 쓰고, `--chip <이름>`으로 고를 수 있다. (판단)
- 엔진 쪽 확인 기능("새 모델을 올려도 되는지 확인")의 범위:
  - `api: openai`인 엔진이면 응답 정확도와 tool calling 검사가 그대로 돈다.
  - "준 설정이 실제로 적용됐는지" 검사는 vLLM과 SGLang 로그 형식을 읽으므로, 그 밖의 엔진에서는 "지원 안 됨"으로 표시하고 건너뛴다. 리포트에 그렇게 적는다.
- AMD (판단): 지금은 AMD에서도 DCGM(NVIDIA 전용) 지표를 쓰는데, 이건 틀린 동작이다. `amd-gpu.yaml`은 지표 수집기를 비워 두고, 대시보드는 "이 칩은 이 지표를 내지 않음"으로 보이게 한다. AMD 지표 수집기 연결은 이번 범위가 아니다. NVIDIA 동작은 그대로다.
- 대시보드와 경보는 공통 이름(`utilization`, `power`, `memory_used`, `temperature`)으로 만들고, 설정 파일의 `metrics`로 실제 지표 이름에 연결한다. 연결이 없는 칸은 패널에 "이 칩은 이 지표를 내지 않음"으로 보인다.

### 3.4 하지 않는 것

- 실제 HyperAccel·Furiosa 칩으로 시험하지 않는다(실물 없음). 예시 파일 `chips/example-npu.yaml`은 값이 `<...>`인 견본이고, 형식 검사 테스트에만 쓴다.
- 엔진 쪽 플러그인(Python 코드 끼우기)은 만들지 않는다. 설정 파일로 안 되는 경우는 다음 단계의 일로 남긴다.

## 4. 몰려도 버티기

### 4.1 복제본과 라우팅

- 복제본 수는 이미 `ops export --target gateway --replicas N`으로 정할 수 있다. 앞단은 이미 llm-d(InferencePool + EPP)다. 이 구성을 그대로 쓴다. (판단: 라우팅을 새로 만들지 않는다)
- 같은 GPU에 복제본 N개를 올리려면 복제본마다 메모리 비율(`--gpu-memory-utilization`)을 나눠야 한다. `GatewayOptions`에 복제본 수를 넣으면 비율을 자동으로 나누게 한다(합 0.85 기준, 측정으로 조정). 쿠버네티스에서 GPU 한 장을 여러 파드가 나눠 쓰는 방법(NVIDIA device plugin의 time-slicing 설정)이 필요하다. 설정 방법과 동작 여부는 데스크탑에서 확인한다.
- time-slicing이 k3s에서 안 되면 (판단): 복제본 파드가 `nvidia.com/gpu`를 요청하지 않게 하고, NVIDIA 런타임(`runtimeClassName: nvidia`)과 `NVIDIA_VISIBLE_DEVICES=all`로 GPU를 직접 보게 한다. 쿠버네티스 밖(일반 Docker)으로 빼지 않는다. 게이트웨이, 청구, 지표가 모두 쿠버네티스 경로에 있기 때문이다. 어느 방법을 썼는지 결과 문서에 적는다.
- 복제본 수를 콘솔에서 바꿀 수 있어야 한다(4.3절). `kubectl scale`로 바꾸고, 새 복제본이 준비될 때까지 기다린다.

### 4.2 실시간 지표 (콘솔 "실시간" 탭, 사용자가 고른 B안)

위쪽 숫자:
- 동시 요청 수
- 첫 글자까지 시간 p99 (목표 대비)
- 글자 사이 간격 p99
- 출력 토큰/초
- 칩 전력(W)
- 시간당 전기료

그 아래:
- 첫 글자 p99의 최근 5분 그래프
- 복제본 표: 상태, 처리 중인 요청, 대기, KV 캐시 사용률, 받은 요청 비율

#### 용량과 여유 (2026-11-13 추가, 사용자 요청)

운영자가 먼저 묻는 "지금 얼마나 차 있고, 얼마나 더 받을 수 있나"를 실시간 탭 맨 위에 둔다. 항목은 큰 클라우드·하드웨어 회사의 공개 문서를 비교해 골랐다(Azure OpenAI PTU 사용률, Vertex AI 예약 용량 사용률 요약, Bedrock `EstimatedTPMQuotaUsage`, SageMaker 엔드포인트 지표, NVIDIA Run:ai 유휴 GPU, NVIDIA Dynamo KV 라우팅 대시보드).

1. **용량 사용률** (원형 그래프, Azure·Vertex 방식): 지금 분당 토큰 ÷ 최대 분당 토큰.
   - 최대 분당 토큰은 부하 시험(4.3절)에서 첫 글자 p99가 목표(기본 1초) 안이었던 가장 높은 단계의 출력+입력 토큰/분으로 잡는다. 어느 시험 기록(시각, 복제본 수, 모델)에서 온 값인지 같이 표시한다.
   - 시험 기록이 없거나 복제본 수·모델이 지금과 다르면 숫자 대신 "부하 시험을 먼저 돌리세요"를 띄운다. 추정값을 만들어 넣지 않는다.
2. **최근 기간 요약** (Vertex 방식): 최근 1시간의 용량 사용률 작은 선 그래프와 최대, 평균, 90 %를 넘은 횟수. (판단: 기간 1시간, 경계 90 %)
3. **용량 부족 신호** (숫자): 게이트웨이가 한도로 거절한 요청(429) 수, 대기 중 요청 수(`vllm:num_requests_waiting` 합), 놀고 있는 복제본 수(Run:ai 방식, 5분 넘게 처리한 요청이 없는 복제본).
4. **고객별 한도 소진률** (막대, Bedrock 방식): 고객마다 분당 토큰 한도 중 지금 쓰는 비율과 최근 1시간 거절 수. 고객별 한도는 이미 테넌트 저장소에 있다.
5. **복제본 표에 추가**: KV 캐시 사용률(`vllm:kv_cache_usage_perc`) 옆에 캐시 적중률(`vllm:prompt_tokens_cached` ÷ `vllm:prompt_tokens`의 최근 5분 비율)과 GPU 사용률(DCGM)을 둔다. GPU 사용률은 "여유"를 직접 말해 주지 않으므로 맨 위 원형에서는 뺀다.

- 원형 그래프는 "전체 중 얼마"인 1번에만 쓴다. 시간에 따라 변하는 값(2, 3번)은 선 그래프나 숫자로 둔다.
- 게이트웨이 429 수와 고객별 분당 토큰을 어느 지표(Envoy·AI Gateway 지표 또는 접근 로그)에서 읽을지는 데스크탑에서 실제 지표 이름을 확인한 뒤 정한다.
- 화면 초안: `docs/specs/mockups/live-capacity.html` (숫자는 예시).
- 나중에: Dynamo Planner처럼 "예측 대 실제"는 자동 증감(로드맵 5번)을 만들 때 넣는다.

- 갱신 주기는 2초. (판단)
- 값은 Prometheus에서 읽는다(이미 배포 스택에 있음). 콘솔 서버가 Prometheus에 질의해서 화면에 넘긴다.
- 지표 이름은 칩 설정 파일의 `metrics`와 엔진 지표(vLLM)에서 온다. 엔진 지표 이름은 프로젝트 1의 데스크탑 확인(Task 12)에서 확정한 것을 쓴다.

### 4.3 부하 시험 (B안의 핵심)

- 콘솔에서 최대 가상 사용자 수(기본 20명)를 정하고 시작 버튼을 누른다. 한 번의 시험은 동시 사용자 1, 5, 10, 20명을 단계마다 15초씩 차례로 돌린다(약 1분). 그래야 고른 B안 그림처럼 "동시 사용자 수별 첫 글자 p99" 곡선이 나온다. (판단: 한 점이 아니라 곡선)
- 콘솔 서버가 guidellm(이미 `measure` extra)을 게이트웨이 주소로 실행한다. 부하 시험 전용 테넌트와 키를 자동으로 만들어 쓰고, 그 사용량은 청구서에서 뺀다. (판단)
- 진행 중에는 위쪽 실시간 숫자가 그대로 움직인다.
- 끝나면 결과(동시 사용자 수별 첫 글자 p99, 출력 토큰/초)를 "실행 기록"으로 저장한다. 복제본 수를 바꿔 다시 돌리면 이전 기록과 같은 그래프에 겹쳐 그린다.
- 실행 기록은 파일로 남긴다(`runs/loadtests/<시각>.json`). 같은 내용을 결과 문서로 꺼낼 수 있다.

### 4.4 복제본 하나 끄기

- 복제본 표에서 하나를 골라 끈다(파드 삭제). 끄는 동안에도 부하 시험이 계속되고, 오류율과 첫 글자 시간이 어떻게 변하는지 보인다.
- 2절 표의 아래쪽 결과(1개가 더 빠름)일 때는 필수다. 위쪽 결과여도 넣는다. (판단: 실제 분산 서비스의 기본 기능이고 구현이 작다)

### 4.5 안전장치 (부하 버튼은 위험하므로)

- 부하 시험, 복제본 수 변경, 복제본 끄기는 운영 콘솔에서만 가능하다. 운영 콘솔은 지금처럼 기본적으로 `127.0.0.1`에서만 열린다.
- 이 세 가지는 누를 때 한 번 더 확인한다(무엇을 얼마나 할지 보여 주는 확인 창).
- 부하 시험은 한 번에 하나만 돈다. 동시 사용자 상한은 100으로 둔다. (판단)
- **맥북에서 이 버튼들을 쓰는 방법 (판단)**: 시연은 맥북에서 콘솔을 여는 장면이다. 운영 콘솔은 계속 `127.0.0.1`에만 열고, 맥북은 `tailscale serve`로 그 포트를 tailnet 안에만 내보내 접근한다. 즉 접근 경계는 "사용자 본인의 tailnet 기기"다. 공개 인터넷에는 열지 않는다. 별도 운영자 로그인은 이번 범위가 아니다. 콘솔의 Host 검사 목록에 그 tailnet 이름을 더하는 옵션(`ops ui --allow-host`)을 둔다.

### 4.6 자동 증감 (2026-11-13 추가, 사용자 결정 "처음부터")

4.2절의 용량 지표를 보여 주는 데서 끝내지 않고, 그 지표로 복제본 수를 자동으로 늘리고 줄인다. 원래 프로젝트 5로 미뤘던 일 중 "늘리기와 최소 1개까지 줄이기"를 여기로 당긴다. 0개까지 내리기(콜드 스타트, 전력 절약)는 프로젝트 5에 남긴다.

**누가 하나 (판단)**: `ops serve`(이미 클러스터 안에 있는 운영 API) 안에 작은 제어 루프를 둔다. KEDA나 HPA를 쓰지 않는 이유는, 판단 근거인 "최대 분당 토큰"이 부하 시험 기록 파일에 있어 Prometheus만으로는 계산이 안 되고, 결정 이유를 콘솔에 그대로 보여 주고 GPU 없이 단위 테스트하기 쉽기 때문이다. 비용: 쿠버네티스 표준 부품이 아니다. 판단이 틀렸다고 보이면 같은 규칙을 KEDA Prometheus scaler로 옮긴다.

**규칙 (숫자는 기본값, 설정 파일로 바꿀 수 있음)**:

| 조건 | 조치 |
|---|---|
| 용량 사용률 ≥ 80 %가 2분 넘게 계속, 또는 대기 중 요청 > 0이 2분 넘게 계속 | 복제본 +1 (최대치까지) |
| 용량 사용률 ≤ 30 %가 10분 넘게 계속이고 대기 0 | 복제본 −1 (최소 1개) |
| 놀고 있는 복제본(5분 넘게 처리 0)이 있고 남은 복제본으로 용량 사용률이 60 % 이하로 예상됨 | 복제본 −1 (최소 1개) |

**흔들림 방지**:
- 늘린 뒤 5분, 줄인 뒤 10분은 같은 방향이든 반대 방향이든 다시 바꾸지 않는다.
- 새 복제본이 준비(ready)되기 전에는 그 복제본을 용량 계산에 넣지 않고, 다음 결정도 하지 않는다.
- 한 번에 1개씩만 바꾼다.

**한 GPU의 한계 (중요)**: 지금 GPU는 한 장이고, 복제본마다 GPU 메모리 비율(`--gpu-memory-utilization`)을 나눠 쓴다(4.1절). 복제본 수가 바뀔 때마다 비율을 다시 나누면 기존 복제본을 모두 재시작해야 해서, 늘리는 순간 서비스가 끊긴다. 그래서 자동 증감을 켜면 **최대 복제본 수 기준으로 비율을 미리 고정한다** (예: 최대 3개 → 각 0.28). 대가로 복제본이 1개일 때도 KV 캐시가 작다. 최대 복제본 수는 칩 설정 파일과 GPU 메모리로 정하고, 콘솔에 "GPU 한 장, 최대 복제본 N개"로 표시한다. 최대 몇 개가 실제로 들어가는지는 데스크탑에서 잰다.

**운영자 조작과 기록**:
- 실시간 탭에 자동 증감 켜기/끄기 스위치를 둔다. 끄면 4.3·4.4절의 수동 조작만 된다. 기본은 켜짐. (판단)
- 결정마다 시각, 이유(어느 지표가 몇 %였나), 조치, 결과(새 복제본이 준비되기까지 걸린 시간)를 기록해 콘솔에 목록으로 보이고 파일(`runs/autoscale/<날짜>.jsonl`)로 남긴다.
- 부하 시험 중에는 자동 증감을 끌지 켤지 시험 시작 화면에서 고른다. 복제본 1개 vs 3개 비교 시험은 끈 상태로 돌린다.

**자동으로 하지 않는 것 (권장 조치로만 띄움)**: 라우터 가중치 조정(한 복제본만 몰릴 때), 고객 한도 조정(한 고객만 한도를 다 쓸 때). 둘 다 콘솔에 권장 문구와 실행 버튼을 둔다. 자동으로 바꾸면 원인 파악 없이 증상만 가리기 쉽기 때문이다. (판단)

**검증 (데스크탑)**: 부하 시험으로 동시 사용자를 1 → 20 → 1로 바꾸며, 복제본이 늘고 주는 시각, 새 복제본 준비 시간, 그동안의 첫 글자 p99와 오류율을 결과 문서에 남긴다.

## 5. 끝났다는 기준 (제품 정의서와 같음)

- 복제본 여러 개와 라우팅이 데스크탑에서 실제로 돈다.
- 콘솔 "실시간" 탭에 실제 지표가 2초마다 갱신된다.
- 콘솔에서 부하 시험을 돌려 복제본 1개와 3개의 결과를 한 그래프에 겹쳐 볼 수 있고, 그 숫자가 결과 문서로 남는다.
- 복제본 하나를 꺼도 서비스가 이어지는지 실측 결과가 있다.
- 부하를 올렸다 내렸을 때 복제본이 자동으로 늘고 주는 실측 기록(시각, 이유, 준비 시간, 그동안의 첫 글자 p99)이 있다.
- NVIDIA·AMD의 박힌 값이 설정 파일로 옮겨졌고, 기존 테스트가 모두 통과한다. 견본 칩 파일이 형식 검사를 통과한다.

## 6. 하지 않는 것

- 기계 여러 대로 된 클러스터.
- 복제본을 0개까지 내리기와 콜드 스타트(프로젝트 5의 일). 자동 증감 자체는 4.6절로 이번에 한다.
- 새 라우팅 알고리즘. llm-d 기본 동작을 쓴다.

## 7. 만드는 방식

- 맥: 칩 설정 파일, 실시간 탭, 부하 시험, 복제본 조작의 코드와 GPU 없는 테스트.
- 데스크탑: spike 측정, time-slicing 설정, 실제 부하 시험, 결과 문서.
- 순서: spike 결과를 보기 전에 3절(칩 설정 파일)과 4.2·4.3절의 화면과 서버 코드를 먼저 만들 수 있다. 4.1절의 메모리 나누기 값과 4.4절의 시연 결론은 spike 결과 뒤에 확정한다.
